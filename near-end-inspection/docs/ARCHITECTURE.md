# 架构说明

## 1. 端侧采集

目标产品在 NXP KL26Z4 微控制器上运行采集程序，通过 ADC16 读取四路模拟信号，并使用 W5500 以太网控制器发送数据。采样中断只完成采集与环形缓冲区入队，报文格式化和网络发送放在主循环中，减少网络操作对实时采样的干扰。

每条记录绑定设备编号、采集时间与四个通道值。发送成功后才推进缓冲区读指针；链路中断、连接关闭或发送空间不足时，保留待发送记录并按策略重连。

## 2. 数据服务

Node.js 服务监听终端 TCP 连接，从字节流中提取以换行符结束的完整记录。解析器保留半行，支持一个数据块中包含多行，只有在设备编号和字段格式都有效时才产生结构化记录。

服务同时提供 WebSocket 通道，向浏览器发送实时帧、增量记录、最近历史和终端在线状态。短期内存缓存用于浏览器重连恢复，不被当作长期数据库。

## 3. Web/PWA 客户端

React 客户端按屏幕宽度选择宽屏工作台或移动端布局。两端复用通道配置，使当前值、趋势、统计、表格和 CSV 表头保持一致。Web 端适合持续观察和完整会话导出，移动端侧重设备近端的最新状态和最近记录。

## 4. 状态模型

系统不使用单一“在线/离线”概括整条链路，而是拆分为：

1. 数据服务连接：浏览器是否连接 WebSocket 服务。
2. 采集终端连接：服务端是否存在终端 TCP 连接。
3. 数据时效：最近数据是否仍在允许的时间窗口内。
4. 页面显示状态：客户端是否主动暂停把新记录写入界面缓存。

这一分层让现场人员先定位采集链路，再判断数据本身，降低把通信异常误认为泵体异常的风险。

## 5. 数据与安全边界

- CSV 是当前版本的主要归档方式，正式任务结束前必须完成导出和文件核对。
- 通道单位和转换关系必须与传感器量程、接线和标定结果一致。
- 生产部署应把端口、主机地址和终端编号放入环境配置，不写死在公开源码中。
- 公开作品版只呈现模拟数据和产品逻辑，不连接现场 TCP、WebSocket 或硬件。
