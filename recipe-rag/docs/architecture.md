# 架构说明与产品判断

## 为什么采用混合检索

菜名、食材名等实体词更适合 BM25 精确匹配，“清淡一点”“适合早上快速完成”这类表达则更依赖语义向量。系统分别生成候选结果，再用 Reciprocal Rank Fusion 合并排序，避免把效果押在单一检索器上。

## 为什么保留父子文档关系

按标题切分能提高检索粒度，但命中“操作步骤”时可能漏掉同一菜谱中的食材和用量。每个子块保存 `parent_id`，检索后可以回溯完整菜谱，在召回精度与上下文完整性之间取得平衡。

## 为什么先路由再生成

“有哪些菜”“需要什么食材”“详细怎么做”需要的答案结构不同。查询路由先判断列表、基础信息或详细说明，再选择对应提示模板；这比使用一个万能提示词更容易控制长度、格式和事实边界。

## 可靠性边界

- 生成模型负责组织语言，菜名、食材和步骤应以检索上下文为依据。
- 检索为空或证据不足时，应明确提示无法确认，而不是补写不存在的做法。
- API 密钥只从环境变量读取，日志与仓库均不记录真实值。
- 本地向量索引不随仓库分发，避免不可信反序列化文件和无效的大体积产物。

## 建议评测方案

准备覆盖菜名精确查询、食材反查、分类推荐、难度过滤和模糊意图的测试集。离线评估 Recall@K、MRR、路由准确率和引用覆盖率；人工评估答案忠实度、完整性、可操作性与拒答合理性。每次调整分块、嵌入模型或融合权重后复跑同一测试集。
